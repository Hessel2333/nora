# 许可证选项（未决）

仓库当前未声明开源许可证。本次审查不替项目所有者做法律或商业选择。

## 待评估选项

- 专有许可证：适合闭源商业 SaaS，但需明确贡献与客户部署条款。
- Source Available：可开放阅读并限制生产/竞争性使用，但不是 OSI 开源；条款设计和社区预期需要法务确认。
- Apache-2.0：宽松且包含专利授权，适合希望建立开放生态的核心代码。
- MIT：最简宽松许可，生态兼容性高，但专利条款和商业控制弱于 Apache-2.0。
- AGPL-3.0：强调网络服务修改回馈，可能影响商业集成与客户私有化策略。
- 双许可证：可同时支持社区与商业授权，但治理成本更高。

## 决策前必须回答

- Nora 是否接受外部贡献？
- 客户私有化部署和二次开发的权利边界是什么？
- 是否会链接或复制 GPL/AGPL 组件？
- 是否采用任何 Source Available 组件，其生产使用、托管或竞争性限制是什么？
- 商标、数据模板、设计资产和代码是否采用同一许可？

## GPL/AGPL 依赖影响

- 仅通过独立网络 API 与 GPL/AGPL 服务通信，和把其代码链接、修改、分发进 Nora，义务不同，必须按具体架构和司法辖区评估。
- GPL 通常聚焦分发衍生作品；AGPL 还增加网络交互场景的源代码提供义务。
- OCA/Odoo/ERPNext 模块不能因“开源”就直接复制；必须记录版本、模块许可证、修改和交付方式。
- 容器化、客户私有部署、插件边界和前端静态资源是否构成组合，需要法务基于实际打包方式判断。

在正式决定前，不添加 LICENSE 文件，也不对外宣称“开源”。
