# ADR-0002：配方时态与递归快照

状态：已接受
日期：2026-08-18

## 背景

历史订单若只保存当前 BOM 引用，发布或退役配方后重新展开会改变既有生产需求，破坏审计、成本和追溯。

## 决策

- 已发布配方版本采用半开有效区间 `[effectiveAt, effectiveTo)`，同一产品区间不可重叠。
- PostgreSQL 使用有效期检查与 GiST 排斥约束，作为并发发布的最终守门。
- 发布命令必须携带草稿 revision；并发约束冲突映射为稳定 HTTP 409，而不是数据库错误。
- API 以 `draft/scheduled/current/historical` 展示时态，避免把未来版本称为当前生效。
- 配方版本生命周期写入追加式审计事件；历史迁移不伪造未知操作者。
- 订单审批按交付时点选择有效版本，并递归冻结完整多层配方快照。
- 生产需求展开只使用快照；旧数据无法证明完整性时失败关闭。
- 重复审批返回同一生产需求。

## 后果

数据体积增加，但历史结果可重放。配方发布必须检查时态冲突；快照需要 schema 版本。

## 验证

单元测试覆盖未来发布、回填重叠、退役历史版本、revision、并发错误映射、嵌套展开和重复审批。数据库迁移增加 `effective_to`、`recipe_snapshot` 与版本审计事件；API smoke 并发发布两个草稿并验证只能一个成功。

## 恢复

迁移为追加列和审计表。若部署回退，旧应用会忽略新结构；数据库恢复应使用部署前备份。不得删除已生成快照或审计事件来“回滚”历史事实。
