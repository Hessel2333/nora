# Nora 关键审查报告

审查日期：2026-08-18；完成度复核：2026-08-20
范围：产品定位、仓库结构、前后端代码、Prisma schema/migrations、测试、CI、原型、会议纪要、功能清单和浏览器实测。

## 结论

Nora 有一个有价值的垂直切口：把中央厨房订单转成可审计的生产依据和现场任务。但当前成熟能力集中在客户/订单/简单生产配方和订单审批后的生产需求；其余大部分是高完成度界面原型。最大风险不是页面不够，而是演示表面曾掩盖后端边界、历史配方会随主数据漂移、模式之间会静默回退，以及仓库缺少持续守门。

本次已直接修复可安全验证的 P0：递归配方快照、配方有效期区间、重复审批幂等、版本化工序与阶段投料、快照 v2、投料/版本数据库作用域守卫、生产模式禁 Mock/假身份、显式生产路由白名单、演示能力可见标识、任务式导航、文档事实源、CI/模板/CODEOWNERS 与迁移验证入口。根据净配菜工厂边界，BOM 主任务进一步收敛为可交互的层级逻辑表和无烹调标准前处理流程；自由缩放关系图退出日常操作主线。

## 值得保留的基础

- Next.js 与 NestJS/Prisma 的模块化单体边界清楚，技术栈适合当前团队规模。
- 订单服务已有事务、revision 乐观锁、组织过滤和审计事件基础。
- 配方条目使用 Decimal 字段，Presenter 负责 API 数值转换，方向正确。
- UI 有一致的 token、卡片/表格/对话框组件，桌面和移动响应式基础较好。
- 原型覆盖了订单到现场的完整叙事，适合用来验证信息架构，只需与生产事实严格隔离。

## 产品边界判断

### 应自研

- 食品制造的配方版本、单位、损耗、阶段投料和历史快照
- 订单汇总到生产需求、合批/拆批和去向保留
- 订单—需求—批次—工单—质量—库存事件的事实链
- 计划员、生产主管和现场员工的任务式体验

### 应集成或参考

- 身份、授权、通用优化求解器、ERP/财务、标准追溯语义
- ERPNext、Odoo/OCA 与观麦用于能力和边界对照，不直接复制为 Nora

### 当前应停止扩张

- 静态“AI”预测与采购建议
- 无设备数据的 3D 数字孪生
- 完整 WMS/MES/财务/CRM 的横向铺开

详细决策见 [Build / Buy / Integrate](../product/build-vs-buy.md)。

## 数据与事务审查

- 配方版本查询必须同时判断 `effectiveAt <= asAt` 与 `effectiveTo > asAt/null`；草稿不参与。
- 发布未来版本只在未来时间关闭上一版本，不能在发布时间提前退役。
- 订单审批的状态、审计事件、需求和快照应处于同一数据库事务。
- 旧生产需求无法可靠还原审批时主数据，迁移标记为不完整而非伪造可信快照。
- 应用层先检查发布时间，PostgreSQL 排斥约束作为并发发布的最终完整性守门；命名约束冲突已映射为稳定 HTTP 409。
- 工序与投料分别建模但由同一配方版本治理；`BomItem(operationId, bomVersionId)` 使用复合外键指向同版本 `BomOperation`，避免仅靠应用约定。
- 新审批快照使用 schema v2，递归冻结工艺步骤与阶段投料；v1 仅作为兼容读取，旧占位快照继续失败关闭。
- 当前库存与成本不具备事实级实现，不能从展示字段推断生产可用性。

## 原始材料审查

- 功能清单包含 142 条新架构功能，优先级覆盖面远大于当前可交付闭环；其中汇总公式存在 `#NAME?`，不可直接作为机器可验证事实。
- 会议纪要明确是 AI 生成且可能不准确，但其“参考成熟 ERP、先做商品/订单/生产最小闭环”的方向与本次边界判断一致。
- 工厂 CAD 可用于业务区域和走线参考；当前前端几何是提取后的展示资产，不是实时设备模型。
