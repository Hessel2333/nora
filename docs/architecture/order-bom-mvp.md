# 订单与 BOM MVP 架构

## 目标

用最小范围跑通一条真实业务链路：

```text
创建订单 → 提交审核 → 审核通过并创建生产需求 → 匹配交期有效 BOM → 多层展开 → 汇总底层物料需求
```

本阶段不包含库存扣减、采购、排产、MES、配送、对账、完整权限和多租户界面。

## 运行结构

```text
Next.js :3000
   │ REST / JSON
   ▼
NestJS :3100/api/v1
   │ Prisma ORM
   ▼
PostgreSQL :54329
```

前端不得直接读取数据库。控制器负责 HTTP 契约，服务负责用例编排与事务，policy 文件保存可独立测试的业务规则，Prisma 负责持久化。

## 数据边界

核心表：

- `organizations`：当前 MVP 使用固定演示组织，所有业务表仍保留 `organization_id`。
- `customers`、`products`：订单和 BOM 所需的最小主数据。
- `sales_orders`、`sales_order_lines`、`sales_order_events`：订单聚合。
- `production_demands`、`production_demand_lines`：审核后生成的生产需求及订单来源快照。
- `boms`、`bom_versions`、`bom_items`：BOM 聚合及版本。
- `document_numbers`：并发安全的业务编号计数。

订单保存客户名称、联系人、地址、商品编码、名称、单位和价格快照，防止主数据后续变化污染历史单据。

数量、价格、成本均使用 PostgreSQL Decimal。不要在数据库中使用浮点数保存业务金额。

## 关键不变量

### 订单

- 同一订单不能重复出现相同商品。
- 只有草稿可修改。
- 状态必须按服务端状态机迁移。
- 写操作使用 `revision` 乐观锁防止覆盖他人修改。
- 每次业务状态变化必须写入事件日志。
- 审核通过、事件写入和生产需求创建必须在同一个事务中完成。
- 一张销售订单只能生成一张生产需求，需求行必须保留原订单行来源。

### BOM

- 一个产出商品只有一个 BOM 聚合，但可以有多个版本。
- 同一版本中不能重复添加相同物料。
- 已生效和已停用版本不可编辑；修改必须复制为新草稿。
- 发布新版本时，同 BOM 的旧生效版本自动停用。
- 展开时按订单交期选择当时已生效版本。
- 展开过程检测循环引用；成品缺少有效 BOM 时显式返回 `missingBoms`。

## 接口版本

所有 MVP 接口位于 `/api/v1`。接口契约由 NestJS DTO 与 OpenAPI 文档定义。破坏性变更必须升级 URL 主版本或提供兼容迁移期。

## 暂未实现的生产能力

- 身份认证和按组织授权
- 数据权限和审计用户 ID
- 单位换算
- BOM 生效时间重叠的数据库级约束
- 批量导入、异步任务和消息事件
- 库存、采购、排产和实际成本

这些能力必须作为独立纵向任务加入，不能悄悄混入订单或 BOM 的普通改动。
