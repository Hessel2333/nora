# 订单、生产需求与生产执行关系

## 本次 MVP 决策

当前已实现以下纵向链路：

```text
销售订单 → 提交审核 → 审核通过并创建生产需求 → 冻结交期有效配方 → 合批/拆批形成草稿生产批次 → 确认批次 → 释放生产工单
```

批次确认与一批次一工单释放已经实现；库存占用、工序拆单、真实 MES 执行仍不在当前实现范围内。订单审核只创建生产需求，不直接创建批次或工单；生产计划员必须显式分配需求，生产主管确认后才能释放工单。

## 对象边界

| 对象 | 回答的问题 | 本次 MVP |
| --- | --- | --- |
| 销售订单 | 客户需要什么、交付给谁、何时送达 | 实现 |
| 生产需求 | 工厂需要生产什么、多少、何时需要 | 实现 |
| 生产计划批次 | 哪些需求合并或拆分、计划何时生产 | 创建、来源分配和确认已实现 |
| 生产工单 | 本批按冻结工艺执行什么、多少、何时开始 | 一批次一工单释放与查询已实现 |

## 审核事务

订单审核采用“自动校验 + 例外人工审核”的目标模式。当前 MVP 暂时由人工批准所有有效订单；权限、策略版本和组织级阈值完成后，低风险订单可由系统自动批准。详细规则见 [订单审核策略](../modules/orders/order-review-policy.md)。

审核通过必须在同一个数据库事务中完成：

1. 校验订单当前状态为 `pending`。
2. 将订单状态更新为 `approved`，并增加 `revision`。
3. 写入订单审核事件和审核意见。
4. 创建一张生产需求单。
5. 按订单行创建生产需求行，并保存商品、数量、单位和交期快照。
6. 按订单交期匹配当时有效的顶层 BOM 版本；缺少 BOM 时保留需求并标记异常，不直接创建工单。

一张销售订单当前只创建一张生产需求单，重复审核不得重复创建需求。

## 聚合与拆分

生产需求必须保留销售订单来源，计划阶段再决定聚合或拆分：

```text
销售订单行 1 ─┐
销售订单行 2 ─┼─→ 生产需求行 ─→ 需求分配 ─→ 生产计划批次 ─→ 工序工单
销售订单行 3 ─┘                         ↑
                                      多对多数量关系
```

当前 `demand_allocations` 保存：

- `production_demand_line_id`
- `production_batch_id`
- `allocated_quantity`

因此系统必须支持：

- 多张订单的相同商品合并为一个生产批次。
- 一条订单需求因批容量、班次、产线或交期被拆成多个生产批次。
- 当前一个生产批次生成一张包含完整有序工艺快照的工单；未来可按产线和工序受控拆单。
- 完工和包装时按需求分配关系回写到原始订单。

## 可合并条件

只有同时满足以下条件的需求才可建议合并：

- 同一工厂和可兼容的交付时间窗。
- 同一商品、规格、包装和计量单位。
- 使用兼容的 BOM 与工艺路线。
- 食品安全、过敏原和客户隔离要求允许共批。
- 批容量、产线能力和保质期允许。

即使合并生产，也必须保留订单、客户和数量分配关系，以支持包装标签、批次追溯和配送拆分。

## 状态边界

```text
销售订单：draft → pending → approved → in_production → delivering → completed → reconciled

生产需求：pending_planning → partially_planned → planned → completed
                                  └──────────────→ cancelled
```

订单审核创建后的生产需求状态为 `pending_planning`。生产计划模块通过 `CreateProductionBatch` 显式迁移为 `partially_planned` 或 `planned`；执行完成和取消尚未实现。

## 界面原则

- 订单审核是完整业务检查，不使用摘要型小弹窗承载。
- 审核工作台必须展示客户与交期、完整商品行、BOM 就绪状态、审核意见和操作记录。
- 审核完成后展示真实的生产需求编号、需求行和 BOM 状态。
- 批次创建后显示“草稿”；只有完成确认和释放命令后才显示正式工单，释放不等于已经开工。
- 审核任务从审核列表进入，也应返回审核列表；订单详情是独立查看入口。
